# EVM 现阶段对接产物清单

## 1. 目的

本文档用于回答一个非常具体的问题：在当前“先改前后端与索引边界，不主动重写 EVM 核心业务语义”的前提下，EVM 合约仓库现阶段必须向前端、后端和索引层交付哪些稳定产物。

本文档是 [docs/EVM-Seven-Layer-Implementation-Checklist.md](docs/EVM-Seven-Layer-Implementation-Checklist.md) 的配套清单，不替代主清单中的实施阶段说明。

---

## 2. 结论

当前 EVM 合约侧最重要的工作，不是继续扩写业务接口，而是补齐“可被前后端和索引层稳定消费的产物”。

交付物如果不稳定，就会导致：

1. 前端继续写死地址和 ABI。
2. 后端执行器无法和合约版本对齐。
3. 索引器无法稳定解码事件和回写 projection。
4. 一次合约升级会同时击穿页面、API、任务系统和对账链路。

---

## 3. 必须交付的产物

### 3.1 ABI 与类型产物

必须交付：

1. 全量权威 ABI。
2. 按模块拆分的 ABI 目录。
3. 对应的 TypeChain 产物或等价强类型封装。

消费方：

1. 前端：只读查询、必要写调用、错误解析。
2. 后端：tx-builder、simulator、executor、confirmation watcher。
3. 索引器：事件 topic 和参数解码。

硬要求：

1. ABI 版本必须可以追踪到合约提交版本。
2. 不允许前端、后端、索引器各自维护一份不同 ABI。
3. ABI 更新必须与部署地址更新一起发布。

### 3.2 环境部署清单

必须交付：

1. 按环境拆分的 deployed addresses 清单。
2. 最少包含 `Registry`、`VaultCore`、关键 View 模块、关键业务模块。
3. 环境标识、chainId、网络名称、发布时间、版本号。

消费方：

1. 前端：初始化 Registry 种子地址。
2. 后端：执行器和 Query service 启动配置。
3. 索引器：事件源地址和起始块配置。

硬要求：

1. 地址清单必须按环境发布，不能只在脚本输出中口头存在。
2. 生产和测试环境地址必须可追溯、可回滚。
3. 不允许页面脚本、后端服务、运维脚本各自抄一份地址常量。

### 3.3 Registry 与模块键清单

必须交付：

1. module keys 权威定义。
2. Registry 绑定关系说明。
3. 哪些模块必须通过 Registry 解析，哪些仅为部署期辅助地址。

消费方：

1. 前端：运行时模块地址解析。
2. 后端：target module 和路由到合约入口的映射。
3. 运维：升级后地址一致性核查。

硬要求：

1. module keys 只能有一个权威来源。
2. 页面禁止本地手算 hash。
3. 若 Registry 口径变化，必须同步更新前后端和索引器文档。

### 3.4 业务动作到合约入口的映射表

必须交付：

1. `deposit`、`withdraw`、`borrow`、`repay`、`claim` 等动作的入口映射。
2. 每个动作需要的参数说明。
3. 是否需要前置 `approve`。
4. 是否允许后端代执行。
5. 失败时常见 revert 分类。

消费方：

1. 前端：构造 intent 和展示交互步骤。
2. 后端：command 标准化、builder 选择、策略校验。

硬要求：

1. 业务动作的产品语义必须先固定，再映射到合约入口。
2. 不允许页面自己发明“近似动作”绕过命令层。

### 3.5 事件字典与索引说明

必须交付：

1. 关键事件定义。
2. 事件语义说明。
3. 哪些事件是业务权威事实，哪些只是观测或调试事件。
4. 事件字段与业务主线的映射方法。

消费方：

1. 索引器：projection 回写与 checkpoint。
2. 后端：command status projection。
3. 对账脚本：事件重放和差异比对。

硬要求：

1. 事件必须足以让索引器反查业务主线。
2. 若事件不能直接给出 `commandKey`，也必须能通过稳定字段间接回溯。
3. 事件格式更新必须伴随兼容策略。

### 3.6 错误语义与确认口径

必须交付：

1. 常见 revert 或自定义错误清单。
2. 广播失败、链上回滚、确认失败、升级窗口等异常说明。
3. receipt、confirmations、finality 的判断标准。

消费方：

1. 前端：友好错误提示。
2. 后端：错误归类、重试和补偿策略。
3. 运维：告警和人工重放流程。

硬要求：

1. 不允许把所有错误都压成“交易失败”。
2. 必须区分可重试、需人工处理、业务拒绝三类错误。

---

## 4. 建议的产物目录结构

建议对外稳定暴露至少以下结构：

1. `abi/`
2. `typechain/`
3. `frontend-config/moduleKeys.ts`
4. `deployments/<env>/addresses.json`
5. `deployments/<env>/manifest.json`
6. `docs/events.md`
7. `docs/errors.md`

其中：

1. `addresses.json` 用于机器消费。
2. `manifest.json` 用于描述版本、环境、发布时间、commit hash。
3. `events.md` 和 `errors.md` 用于给前后端、索引器和运维团队统一语义。

---

## 5. 发布与同步规则

### 5.1 发布规则

每次 EVM 合约升级或重新部署，必须同时发布：

1. 新 ABI
2. 新地址清单
3. manifest 版本信息
4. 受影响的事件和错误说明

### 5.2 同步规则

当前工作区同步这些产物时，必须满足：

1. 前端、后端、索引器消费同一版本。
2. 不允许只更新前端 ABI，不更新后端执行器。
3. 不允许只更新部署地址，不更新索引器事件源。

### 5.3 验收规则

一次对接物发布完成后，至少应通过：

1. Registry 解析验证。
2. 最小写路径模拟或 smoke test。
3. 关键事件解码验证。
4. 前后端环境配置对齐检查。

---

## 6. 最小验收清单

- [ ] ABI 可由前端、后端、索引器共同消费
- [ ] 地址清单按环境发布且可追溯
- [ ] module keys 和 Registry 绑定关系可机器读取
- [ ] 业务动作到合约入口映射已固定
- [ ] 关键事件具备业务语义说明
- [ ] 错误分类和 finality 口径已固定
- [ ] 当前工作区不再依赖 mock ABI 和 mock 地址作为生产依据

---

## 7. 一句话结论

EVM 现阶段最需要补齐的不是“更多接口”，而是“可被统一前后端和索引层稳定消费的合约产物包”。

## 8. 当前仓库验收表（截至 2026-03-25）

下表基于当前工作区可见产物进行核查，目的是回答一个更落地的问题：按本文档口径，现阶段 EVM 合约仓库是否已经具备“可交付给前端、后端、索引层统一消费”的产物。

| 验收项 | 当前状态 | 依据 | 备注 |
|---|---|---|---|
| ABI 可由前端、后端、索引器共同消费 | 部分满足 | 仓库已有 `abi/` 目录，且存在 `types/` 强类型产物 | 基础产物已存在，但是否已被前端、后端、索引器统一锁定到同一发布版本，当前仓库内看不到完整发布闭环 |
| 地址清单按环境发布且可追溯 | 部分满足 | 已存在 `scripts/deployments/localhost.json`、`scripts/deployments/arbitrum-sepolia.json`、`frontend-config/contracts-localhost.ts`、`frontend-config/contracts-arbitrum-sepolia.ts` | `localhost` 口径基本一致；`arbitrum-sepolia` 前端配置与脚本部署产物存在漂移，不满足“统一权威地址源” |
| module keys 和 Registry 绑定关系可机器读取 | 部分满足 | 已有 `frontend-config/moduleKeys.ts`，且标注 SSOT 来自 `contracts/src/constants/ModuleKeys.sol` | module keys 产物基本成立，但部分消费侧仍有手写 keccak 常量，说明尚未完全收口到唯一来源 |
| 业务动作到合约入口映射已固定 | 部分满足 | 多份架构文档已经描述 `deposit`/`withdraw`/`repay`/`liquidate` 等主路径 | 当前更多是分散在说明文档中，尚未形成单独、稳定、可直接交付的 action-to-entry 映射表 |
| 关键事件具备业务语义说明 | 未满足 | 仓库存在若干事件相关说明文档和实现文档 | 本文建议的 `docs/events.md` 尚未形成固定交付件，索引层统一消费口径仍不够集中 |
| 错误分类和 finality 口径已固定 | 未满足 | 仓库存在错误生成脚本、部分模块错误文档、监控说明文档 | 本文建议的 `docs/errors.md` 尚未形成固定交付件；finality、确认、补偿口径也未看到单一权威文档 |
| 当前工作区不再依赖 mock ABI 和 mock 地址作为生产依据 | 部分满足 | 仓库同时存在真实部署产物、mock 资产清单、mock suite 产物 | 当前目录结构中 mock 与非 mock 产物并存，且 `arbitrum-sepolia` 存在多份地址口径，生产依据仍需进一步收口 |
| manifest 版本信息可对外发布 | 未满足 | 当前仓库未见 `deployments/<env>/manifest.json` 固定产物 | 缺少版本号、发布时间、commit hash、环境元信息这一层可追溯发布件 |
| 前端、后端、索引器消费同一版本 | 部分满足 | 本地 `localhost` 前端配置与脚本部署产物基本一致 | 远端环境仍存在配置漂移；当前更像“仓库内可联调”，还不是“统一版本可签收” |
| 发布后具备最小验收闭环 | 部分满足 | 仓库内已有 smoke / e2e / 预发布脚本 | 脚本能力较强，但未与本文要求的 manifest、事件字典、错误字典、统一地址清单组成单一发布包 |

### 8.1 当前判断

如果判断标准是“仓库是否已经具备联调能力”，答案是：**基本具备**。

如果判断标准是“仓库是否已经具备可稳定对外发布的 EVM 对接产物包”，答案是：**尚未完全具备**。

更准确地说，当前状态属于：

1. ABI、类型、module keys、部署产物、脚本验证能力已经有基础。
2. 但权威地址源、manifest、事件字典、错误/finality 字典这几项仍未形成稳定发布出口。
3. 因此现在更接近“工程上可联调”，而不是“交付上可签收”。

### 8.2 当前最缺的 4 件事

1. 收口为唯一权威地址源，消除前端配置、脚本部署文件、对外地址文件之间的漂移。
2. 补齐 `manifest.json`，把版本、环境、发布时间、commit hash 固定为机器可读产物。
3. 补齐 `docs/events.md`，把关键事件、业务语义、索引映射、兼容策略收口为单一文档。
4. 补齐 `docs/errors.md`，把常见 revert、自定义错误、错误分类、确认/finality 口径收口为单一文档。

### 8.3 部署前必须确认的内容

下列事项不应等待链上部署完成后才开始确认，而应在部署前就形成明确规则；部署后只做“结果核对”，而不是临时补定义。

#### A. 地址产物规则

部署前必须确认：

1. 哪一类文件是环境地址的唯一权威来源。
2. 前端配置是否由该权威来源自动生成，而不是手工维护。
3. 是否允许 `deployments/`、`scripts/deployments/`、`frontend-config/` 同时存在同环境多份地址口径。
4. mock 地址文件与生产地址文件如何隔离命名，避免误消费。

部署后再确认：

1. 某次部署生成的具体地址值是否真实可用。
2. 前端配置、后端配置、索引器配置是否与该次部署结果完全一致。

#### B. Manifest 结构

部署前必须确认：

1. `manifest.json` 的固定字段结构。
2. 版本号规则。
3. 环境标识规则。
4. `commit hash`、生成时间、发布批次等元信息的记录方式。
5. manifest 由谁生成、在什么步骤生成、是否纳入 CI 或 release 流程。

部署后再确认：

1. manifest 中记录的版本、时间、地址引用是否与本次部署一致。

#### C. 事件字典

部署前必须确认：

1. 哪些事件属于关键业务事件。
2. 哪些事件属于观测/调试事件，不作为业务权威事实。
3. 事件字段如何映射到索引层业务主线。
4. 事件变更时的兼容策略如何定义。

部署后再确认：

1. 真实部署版本是否确实发出这些事件。
2. 索引器是否能按字典成功解码并回写 projection。

#### D. 错误与确认口径

部署前必须确认：

1. 常见 custom errors / revert 的分类规则。
2. 可重试、业务拒绝、需人工处理三类错误的划分。
3. `receipt`、`confirmations`、`finality` 的系统口径。
4. 前端提示、后端重试、运维告警是否共享同一套错误映射。

部署后再确认：

1. 真实环境里高频失败场景是否落在既有分类内。
2. 特定网络的确认阈值、告警阈值是否需要按运行经验微调。

### 8.4 实施顺序建议

建议按以下顺序实施：

1. 先在仓库内固定地址产物规则、manifest 结构、events/errors 文档结构。
2. 再把这些结构接入部署脚本或发布流程，使其自动生成或自动更新。
3. 最后在每次部署后执行一致性核对，确认前端、后端、索引器消费的是同一次发布产物。
