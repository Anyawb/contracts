# EVM 错误与确认口径

## 1. 目的

本文档定义当前 EVM 合约仓库对前端、后端、运维团队需要共享的错误分类与确认口径。

目标不是把所有链上失败都压成“交易失败”，而是统一回答：

1. 哪类失败属于业务拒绝。
2. 哪类失败属于权限或配置错误。
3. 哪类失败可以重试。
4. 前端提示、后端补偿、运维告警应如何共用同一套分类。

## 2. 权威来源

当前错误口径的主要来源是：

1. `src/errors/StandardErrors.sol`
2. 模块接口中的 custom errors
3. 运行时 best-effort 失败事件与观测事件
4. 部署/监控相关文档中已固定的异常处理原则

默认规则：

1. 链上 custom error 是第一层来源。
2. 链下广播、确认、RPC 异常是第二层来源。
3. best-effort push 失败默认不等价于主业务失败。

## 3. 错误分类

### 3.1 业务拒绝

定义：

1. 调用成功上链但因业务条件不满足而回滚。
2. 重试同一参数通常不会成功，必须先改变业务状态或用户输入。

典型例子：

1. `InsufficientCollateral()`
2. `HealthFactorTooLow()`
3. `NotEnoughDebt()`
4. `Overpay()`
5. `AssetNotAllowed()`
6. `GuaranteeAlreadyProcessed()`
7. `GuaranteeNotActive()`
8. `BorrowerCannotBeLender()`

处理规则：

1. 前端应给出明确业务提示，不应默认提示“稍后重试”。
2. 后端不应盲目重试同一命令。
3. 运维无需按基础设施故障升级处理，除非该错误异常激增。

### 3.2 权限与配置错误

定义：

1. 调用条件本应满足，但由于角色、Registry、模块绑定、环境配置错误导致失败。
2. 这类错误通常反映部署漂移、角色缺失、模块缺失或脚本配置错误。

典型例子：

1. `MissingRole()`
2. `AccessControlManager__MissingRole(...)`
3. `Registry__ModuleNotFound()`
4. `ModuleNotRegistered(...)`
5. `ModuleKeys__UnknownModuleKey(...)`
6. `PriceUpdater__AssetNotConfigured()`
7. `PriceOracle__AssetNotSupported()`

处理规则：

1. 前端应提示“系统配置异常”或“当前环境不可用”，而不是提示用户修改输入。
2. 后端应停止自动重试同一调用，转为告警或人工处理。
3. 运维应优先检查 Registry 绑定、角色授权、部署产物一致性。

### 3.3 参数与调用错误

定义：

1. 调用方传入的参数非法或上下文非法。
2. 通常是前端、后端 builder、脚本、执行器本身的输入问题。

典型例子：

1. `AmountIsZero()`
2. `RepayAmountZero()`
3. `ZeroAddress()`
4. `InvalidAmounts()`
5. `InvalidGuaranteeAmount()`
6. `InvalidGuaranteeId()`
7. `InvalidNonce(...)`
8. `InvalidSignature(...)`

处理规则：

1. 前端应在交易前做尽可能多的本地校验。
2. 后端 builder 应在签名前拦截。
3. 这类错误不应进入“可重试”队列。

### 3.4 可重试基础设施错误

定义：

1. 失败不来自业务逻辑，而来自 RPC、广播、nonce、网络拥堵、临时节点状态异常等链外问题。
2. 参数不变的情况下，重试可能成功。

典型例子：

1. 广播失败
2. RPC 超时
3. gas estimation 临时失败
4. nonce 冲突
5. provider 短时不可用

处理规则：

1. 前端可以提示“网络繁忙，请重试”。
2. 后端可以按幂等键做有限次数重试。
3. 运维应观察是否为单点 RPC 故障或全局节点异常。

### 3.5 观测与镜像失败

定义：

1. 主账本路径已成功，但 View push、缓存 push、镜像写入、观测上报失败。
2. 这类失败不等价于资金或债务账本失败。

典型例子：

1. `RewardViewPushFailed`
2. `HealthPushFailed`
3. `CacheRefreshAttempted(..., ok=false, ...)`
4. `PriceUpdateFailed`

处理规则：

1. 前端不应直接把订单判定为失败。
2. 后端应走补偿、重试或回源主账本读取。
3. 运维应监控这类事件的趋势，因为它们会影响索引与读模型稳定性。

## 4. 交易状态与确认口径

### 4.1 状态机

建议统一使用以下状态：

1. `created`：命令或用户意图已生成，尚未广播。
2. `broadcast_failed`：未成功广播到链。
3. `submitted`：交易已进入 mempool 或被节点接受。
4. `mined`：交易已打包进区块并拿到 receipt。
5. `reverted`：receipt 存在但链上执行回滚。
6. `confirmed`：已达到环境定义的确认数。
7. `finalized`：已达到系统定义的 finality 口径。

### 4.2 receipt / confirmations / finality

统一原则：

1. `receipt` 表示“已上链执行”，不等于“最终完成”。
2. `confirmations` 表示“已被后续区块覆盖的深度”。
3. `finality` 表示系统认可该交易足够稳定，可以结束主流程。

当前建议：

1. 本地链、开发链可将 `mined` 近似视作 `confirmed`。
2. 公共测试网与生产网的 `confirmed`/`finalized` 阈值应由环境 manifest 或发布流程固定。
3. 前端、后端、运维必须共享同一阈值，不允许各自使用不同确认数。

### 4.3 前端口径

前端至少区分：

1. 用户拒签
2. 广播失败
3. 业务拒绝
4. 系统配置异常
5. 已上链待确认
6. 已确认完成

### 4.4 后端口径

后端至少区分：

1. 可重试基础设施错误
2. 业务拒绝
3. 配置/部署错误
4. 需人工介入
5. 镜像/索引补偿任务

## 5. 当前推荐映射

| 错误类别 | 是否可重试 | 前端提示方向 | 后端动作 | 运维动作 |
|---|---|---|---|---|
| 业务拒绝 | 否 | 修改输入或等待业务状态变化 | 标记为业务失败 | 仅在异常激增时关注 |
| 权限/配置错误 | 否 | 系统暂不可用 | 停止重试并告警 | 检查部署/角色/Registry |
| 参数错误 | 否 | 输入非法 | 拦截并修正调用参数 | 一般无需介入 |
| 基础设施错误 | 是 | 网络繁忙，请稍后重试 | 有限次数重试 | 关注 RPC / 节点健康 |
| 观测/镜像失败 | 视情况 | 读数据可能延迟 | 补偿、重试、回源读取 | 关注索引和缓存健康 |

## 6. 兼容规则

错误与确认口径更新必须遵守：

1. 新增 custom error 时，需要补充本文档分类。
2. 改变错误处理策略时，需要同步更新前端、后端、运维口径。
3. 改变确认数或 finality 规则时，必须同步更新对应环境 manifest 或发布配置。
4. 不允许把所有失败统一压缩成“交易失败”。

## 7. 当前范围说明

本文档是现阶段 EVM 对接的稳定错误口径初版，重点覆盖：

1. 业务主路径错误分类。
2. Registry/角色/模块配置错误。
3. 广播、确认、finality 口径。
4. 缓存与镜像失败的补偿原则。

更细粒度的模块专属错误可在后续版本中继续追加，但不得与本文件冲突。
