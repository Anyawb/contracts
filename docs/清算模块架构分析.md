# 清算模块架构分析（非资金链版）

> 约束：本文件只描述清算模块的“模块边界 / Registry keys / 权限 / 可观测性 / 只读口径”。
>
> 不复述任何资金链、托管关系、资产去向、内部调用串联或 step-by-step 执行流程。
>
> 借贷资金链（含放款/还款/结算/清算分支的资金去向口径）唯一权威：`docs/Usage-Guide/Funds-Flow-Architecture-Guide.md`。

## 📁 文件结构概览

清算模块位于 `src/Vault/liquidation/`，采用模块化设计：

```
src/Vault/liquidation/
├── types/
│   ├── LiquidationTypes.sol            # 类型/事件/常量
│   └── [REMOVED] LiquidationBase.sol   # 已移除：历史底座（易导致估值/职责分叉）
│
├── libraries/
│   ├── LiquidationAccessControl.sol        # 权限控制（ACM 统一权限）
│   ├── LiquidationValidationLibrary.sol    # 参数/数组校验
│   ├── LiquidationRiskLib.sol              # 风险/健康因子核心计算（bps 口径）
│   ├── LiquidationRiskQueryLib.sol         # 风险查询聚合（best-effort 拉取只读数据）
│   └── ModuleCache.sol                     # Registry 地址缓存
│
└── modules/
    ├── SettlementManager.sol               # ⭐ 对外写入口 SSOT：结算/清算状态机
    ├── LiquidationManager.sol              # ⭐ 清算执行器（被 SettlementManager 编排；也保留 role-gated 应急入口）
    ├── LiquidationRiskManager.sol          # 风控只读聚合/缓存
    ├── LiquidationCalculator.sol           # 只读预览/派生计算
    ├── LiquidationConfigManager.sol        # 配置基类（cache + access control + refresh）
    ├── LiquidationConfigModule.sol         # 配置 SSOT：阈值/最小健康因子等
    └── LiquidationPayoutManager.sol        # 残值分配 SSOT：recipients/rates & shares 计算
```

## 🧩 模块职责与边界

### ⭐ SettlementManager（legacy / 通用订单对外写入口 SSOT）

- **职责**：统一承接“还款结算 + 被动清算/强制处置”的状态机分支；对外收口写入口，避免多入口口径漂移。
- **对外入口（keeper）**：`settleOrLiquidate(orderId)`
- **blocks-only 例外**：blocks-only 订单的 keeper 收尾入口不在本模块，而在 `BlocksOnlyCoordinator.settleOrLiquidateBlocks(orderId)`。
- **对外入口（还款编排）**：`repayAndSettle(...)`（由 `VaultCore` 代理调用）
- **约束**：资金语义、资产去向、分支资金处理细节不在本文件复述（见 Funds-Flow SSOT）。

### ⭐ LiquidationManager（清算执行器）

- **职责**：执行清算写入动作（由 `SettlementManager` 编排触发）；并负责 best-effort 的 View 推送。
- **应急入口**：保留 role-gated 的显式参数入口（用于测试/应急/手工处置），但不应成为常态业务主入口。

### LiquidationRiskManager / LiquidationCalculator（只读侧）

- **RiskManager**：聚合只读数据，输出健康/风险评估（受 `maxBatchSizeVar` 约束，避免 DoS）。
- **Calculator**：只读预览与派生计算；不承载写入放行。
- **口径**：核心计算委托 `LiquidationRiskLib`；只读聚合取值委托 `LiquidationRiskQueryLib`。

### LiquidationConfigModule / LiquidationPayoutManager（配置 SSOT）

- **ConfigModule**：清算阈值、最小健康因子等参数的唯一权威写入与事件。
- **PayoutManager**：残值 recipients/rates 配置与 shares 计算的唯一权威。

## 🧭 Registry Keys（依赖解析）

清算相关模块通过 `ModuleKeys` 注册并由 Registry 解析依赖（以部署脚本为准，本文件只列“模块边界”）：

- `KEY_SETTLEMENT_MANAGER` → `SettlementManager`
- `KEY_LIQUIDATION_MANAGER` → `LiquidationManager`
- `KEY_LIQUIDATION_PAYOUT_MANAGER` → `LiquidationPayoutManager`
- `KEY_LIQUIDATION_VIEW` → `LiquidatorView`
- `KEY_LIQUIDATION_RISK_MANAGER` → `LiquidationRiskManager`

此外清算模块会依赖若干“账本/只读聚合模块”（例如 CM/LE/View）。这些依赖的资金链语义与资产去向不在本文件定义（见 Funds-Flow SSOT）。

## 📣 可观测性（DataPush / best-effort）

- **推送目标**：`LiquidatorView`（通过 `KEY_LIQUIDATION_VIEW` 获取）
- **推送方式**：单笔 `pushLiquidationUpdate()`；批量 `pushBatchLiquidationUpdate()`
- **容错机制**：View 推送失败会发出 `CacheUpdateFailed`（用于链下重试）；best-effort 的失败不应改变已完成的账本写入结果

## 🔐 权限控制

本仓库统一以 `ActionKeys` 常量为准（不要在文档里手写 `keccak256(...)`，避免口径漂移）：

- `ActionKeys.ACTION_LIQUIDATE`：keeper/机器人触发清算分支
- `ActionKeys.ACTION_UPGRADE_MODULE`：模块升级（UUPS）

权限授予以部署脚本为准；文档层面只要求：

- keeper/机器人具备触发清算入口所需的 role
- 合约内部编排调用的 role 与 caller 约束不被绕开

## 🛠️ 关键库文件说明

### LiquidationRiskLib.sol

- **功能**：风险评估核心计算
- **包含**：健康因子计算（bps）、风险等级判定、派生安全边际计算

### LiquidationRiskQueryLib.sol

- **功能**：只读聚合取值
- **包含**：从 `Registry` 解析依赖模块并 best-effort 拉取估值/债务等只读数据（不直接绑定 Oracle/GD 的额外接口）

### ModuleCache.sol

- **功能**：模块地址缓存
- **目的**：减少 Registry 查询，提升 Gas 效率

### [REMOVED] LiquidationViewLibrary.sol

- **状态**：已移除
- **原因**：历史实现包含与当前口径不一致的职责边界与计算口径，容易造成重复实现与链下口径分叉
- **替代方案（SSOT）**：
  - 风险计算：`LiquidationRiskLib`
  - 只读聚合取值：`LiquidationRiskQueryLib`
  - 只读/缓存/事件聚合：优先使用各专属 View（如 `LiquidatorView`、`RiskView`、`HealthView`）

## 🔄 升级机制

清算模块采用 **UUPS Proxy** 模式：

1. 部署新实现合约
2. 调用 `upgradeTo(newImplementation)`（需要 `ActionKeys.ACTION_UPGRADE_MODULE` 权限）
3. 新实现自动生效

## 🎯 最佳实践（接口使用层面）

1. **清算前检查**：使用 `LiquidationRiskManager` 或 `HealthView` 获取健康因子与可清算判定。
2. **清算触发入口**：legacy / 通用订单下，keeper/机器人以 `SettlementManager.settleOrLiquidate(orderId)` 为常态入口；blocks-only 下，keeper/机器人以 `BlocksOnlyCoordinator.settleOrLiquidateBlocks(orderId)` 为常态入口。
3. **应急入口边界**：`LiquidationManager.liquidate(...)` 属于 role-gated 显式参数入口，仅用于测试/应急。
4. **错误处理**：监听 `CacheUpdateFailed`，实现链下重试；不要把 View 推送当成强一致前置条件。

## 📌 总结

- 写入口收口：`SettlementManager` 是对外写入口 SSOT
- 执行与只读分离：`LiquidationManager`（写）/ `LiquidationRiskManager`（读）/ `LiquidationCalculator`（预览）
- 配置收口：`LiquidationConfigModule` 与 `LiquidationPayoutManager` 是配置 SSOT
- 可观测性：`LiquidatorView` DataPush + `CacheUpdateFailed`（best-effort）

资金链、资产去向、费用分配与清算分支的资金语义以 `docs/Usage-Guide/Funds-Flow-Architecture-Guide.md` 为唯一权威。
